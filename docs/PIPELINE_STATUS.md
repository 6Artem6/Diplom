# Статус пайплайна детекции UI и текста

## Обязательное заявление

**Текущая реализация (CV + эвристики) является экспериментальной.**

- **Не гарантирует корректность** детекции UI-элементов и текста на реальных скриншотах (Bootstrap, современный веб).
- **Не решает надёжно** задачу детекции UI-текста вне контролируемых условий.
- Дальнейшее усложнение эвристик признано **тупиковым путём**.

Система упёрлась в предел CV-подхода: контурная логика не даёт корректной иерархии и семантики. Для стабильной работы необходим **DL-детектор семантического layout**, а не вывод смысла из контуров.

---

## Наблюдаемые ограничения (воспроизводимые)

| Проблема | Факт |
|----------|------|
| **text_region по факту не работает** | Нет стабильной детекции текста вне кнопок; блоки либо не детектятся, либо деградируют в button/badge/pill. Paddle text detection для text_region не даёт ожидаемого результата в текущей связке. |
| **Кнопки/бейджи по геометрии** | Типы задаются формой (контуры, fill), а не смыслом. Большие контейнеры ошибочно становятся button; маленькие secondary/ghost кнопки и бейджи теряются. |
| **Нестабильное объединение регионов** | Вложенные и пересекающиеся регионы сохраняются; правила 90% / 75%+центр недостаточны; один текст может попадать в несколько регионов. |
| **Debug ≠ результат** | text_boxes, видимые в debug, не доходят до финального результата или исчезают без объяснимой причины. |

## Текущая архитектура (почему изменения не дают эффекта)

1. **Debug-пайплайн** вызывает `run_ui_regions` → при успешном DL всё равно выполняется **CV second pass** (`_second_pass_children_in_roi`) внутри каждого родителя. Типы button/badge/pill/input_like задаются **контурами**, а не моделью.
2. **Flow-пайплайн** использует `cv_detect_regions` (region_prepass) и вообще не использует layout-first UI regions — другой путь, без DL layout.
3. Поэтому правки в эвристиках (merge, badge/button по тексту и т.д.) либо не задействованы в реально исполняемой цепочке, либо перекрываются контурной классификацией.

---

## Обязательный следующий шаг: переход на DL для layout + text

### Требуемая замена

**Заменить `cv_detect_ui_regions` (и гибрид DL+CV) на DL-детектор layout с сохранением остального пайплайна.**

Минимально приемлемый вариант:

1. **Layout detection (обязательно)**  
   Один из: PaddleOCR Layout Detection, LayoutParser (Detectron2), готовая модель на RICO / PubLayNet / UI datasets.  
   Выход: `[{ "x", "y", "w", "h", "type": "button|text|image|list|input|badge|container" }]`.

2. **Text detection**  
   Paddle text detection **по всему изображению**, затем привязка text_boxes к layout-блокам по overlap.

3. **Упрощение логики**  
   - Удалить: классификацию button/badge по fill/contours, большую часть size-heuristics.  
   - Оставить: группировку строк/параграфов, OCR, post-processing.

### Реализованный DL-only путь (без CV second pass)

- **`dl_detect_layout_only(image_path)`** — только LayoutParser (PubLayNet), без CV second pass. Типы: card, section, text_region.
- **`run_ui_regions_dl_only(image_path)`** — то же + fallback на CV при ошибке/отсутствии layoutparser.
- **`run_full_pipeline(image_path, use_dl_only=True)`** — layout из DL-only, **Paddle text detection по всему изображению**, привязка text_boxes к регионам по overlap, группировка строк/параграфов, OCR. Никакой классификации button/badge по контурам.
- В API: **POST /debug/full-pipeline** с полем формы **use_dl_only=true** для включения этого пути.

### Ограничение PubLayNet

LayoutParser (PubLayNet) даёт типы: Text, Title, List, Table, Figure → маппинг в text_region/section/card. **Типов button, input, badge в PubLayNet нет.** Для различения кнопок/инпутов/бейджей по типу модели нужна модель на UI-датасетах (RICO, WebSR и т.п.).

## Definition of Done (обновлённый)

Система считается рабочей, когда:

- обычный текст детектируется стабильно;
- кнопки ≠ бейджи ≠ текст по **типу модели**, а не по размеру;
- маленькие и бледные элементы видны;
- нет вложенных регионов-дубликатов;
- debug == результат (ничего не исчезает без причины);
- правила становятся проще, а не сложнее.

---

## Если DL-модель не внедряется сейчас

Необходимо явно фиксировать в коде и документации:

- текущая реализация **экспериментальная**;
- **не гарантирует корректность** детекции UI и текста;
- **не решает надёжно** задачу детекции UI-текста.

Без такой фиксации дальнейшая «доработка» эвристик создаёт иллюзию прогресса.
